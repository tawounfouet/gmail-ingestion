# Gmail Ingestion 0.4.0a1 — Checkpoint Foundation

## Status

**Alpha implementation slice.**

This is the first implementation step of:

```text
0.4.0 — Incremental History Sync
```

It establishes durable checkpoint semantics before any Gmail History API behavior is introduced.

## Objective

Move the connector from a purely stateless snapshot foundation toward stateful synchronization
without changing the frozen `0.3.0` data-selection or hydration behavior.

```text
0.3.0 stable
   ↓
persistent checkpoint control plane
   ↓
0.4.0a1
   ↓
history.list in 0.4.0b1
```

## Contracts introduced

### Domain model

```text
GmailCheckpoint
├── account_id
├── history_id
├── run_id
├── dataset_version
├── state
├── created_at
├── committed_at
├── invalidated_at
└── invalid_reason
```

### States

```text
CANDIDATE
COMMITTED
INVALID
```

### Persistence interface

```python
class GmailCheckpointStore(Protocol):
    def load_committed(self, account_id: str) -> GmailCheckpoint | None: ...
    def save_candidate(self, checkpoint: GmailCheckpoint) -> None: ...
    def load_candidate(self, account_id: str, run_id: UUID) -> GmailCheckpoint | None: ...
    def commit(self, checkpoint: GmailCheckpoint, ...) -> GmailCheckpoint: ...
    def discard_candidate(self, account_id: str, run_id: UUID) -> None: ...
    def invalidate(self, account_id: str, reason: str, ...) -> GmailCheckpoint: ...
```

## Checkpoint schema

```text
checkpoint_schema_version = 1
```

Checkpoint schema versioning is independent of:

```text
connector package version

```

## Filesystem durability model

```text
accounts/
└── <account_id>/
    └── checkpoints/
        ├── committed.json
        ├── invalid.json
        └── candidates/
            └── <run_id>.json
```

Writes use a temporary file, `fsync`, and atomic `os.replace` before the candidate pointer is
removed.

## Safety invariant

The central invariant of the alpha is:

> A candidate checkpoint must never replace the last committed checkpoint merely because it was
> discovered or persisted.

Conceptually:

```text
H100 COMMITTED
   ↓
run discovers H125
   ↓
H125 CANDIDATE
   ↓
processing succeeds
   ↓
write H125 COMMITTED
   ↓
remove H125 candidate
```

If the run fails before promotion:

```text
H100 COMMITTED remains authoritative
H125 CANDIDATE may be discarded
```

## Invalidation

A committed checkpoint can be marked invalid with a reason. The invalid record is persisted before
the committed pointer is removed.

This prepares the later `historyId` expiration flow:

```text
history.list
   ↓
HTTP 404
   ↓
invalidate committed checkpoint
   ↓
full resync
   ↓
new committed checkpoint
```

The API call and resync orchestration are **not** part of this alpha.
