# Gmail Ingestion 0.4.0rc1 — Incremental Reliability

## Status

**Release candidate qualified by automated CI.**

This milestone closes the reliability scope of `0.4.0`. It does not add new Gmail mutation
types; it makes the existing incremental transaction replayable and safe around crashes,
concurrency and expired cursors.

## Reliability model

```text
COMMITTED H100
    ↓
users.history.list(startHistoryId=H100)
    ↓
freeze History page
    ↓
PENDING event
    ↓
persist effect
    ↓
persist durable receipt
    ↓
PROCESSED event
    ↓
...
    ↓
CANDIDATE H125
    ↓
READY_TO_COMMIT
    ↓
CAS expected H100
    ↓
COMMITTED H125
```

The authoritative cursor changes only at the final compare-and-swap promotion.

## Same-run replay

A restarted run reopens its existing transaction evidence.

For each History page:

```text
page already frozen
→ read immutable RAW
→ do not call users.history.list for that page
```

For each event:

```text
event PROCESSED
→ skip effect

event PENDING + message RAW already exists
→ reuse RAW
→ create receipt
→ mark PROCESSED

event PENDING + no effect yet
→ continue reducer
```

This preserves the immutable-RAW rule while still allowing a run to resume.

## Durable cross-run receipts

Receipt layout:

```text
accounts/
└── <account_id>/
    └── history_receipts/
        └── <event_id[:2]>/
            └── <event_id>.json
```

Receipt payload:

```text
history_receipt_schema_version = 1
account_id
event_id
history_id
event_type
message_id
label_id
source_run_id
applied_at
```

A later run observing the same deterministic `event_id` can prove that its logical effect was
already applied and avoid repeating it.

## Checkpoint compare-and-swap

Promotion can require:

```text
expected_committed_history_id = H100
```

If another run has already changed the committed cursor, promotion fails with
`CheckpointConflictError`.

Snapshot bootstrap can require:

```text
require_no_committed = true
```

This prevents a recovery snapshot from overwriting a checkpoint that appeared concurrently.

Invalidation after an expired Gmail cursor also verifies the expected input history ID before
removing the committed pointer.

## Candidate recovery

If a crash happens after candidate persistence but before commit:

```text
same run_id
+ candidate exists
+ predecessor still matches
→ commit candidate
→ no Gmail call
```

If commit happened but the final manifest did not persist:

```text
committed.run_id == run_id
→ return RECOVERED_COMMIT
→ no Gmail call
```

## Expired/missing cursor recovery

The high-level `ReliableIncrementalSync` performs:

```text
IncrementalHistorySync
    ↓ MissingCommittedCheckpointError / FullResyncRequiredError
FullMessageSnapshot
    ↓
require status == COMPLETED
    ↓
bootstrap checkpoint at snapshot.history_start
    ↓
IncrementalHistorySync catch-up
    ↓
final committed checkpoint
```

A `PARTIAL` or `FAILED` snapshot is never accepted as a synchronization baseline.

## CLI

Default reliable mode:

```bash
gmail-ingest incremental \
  --checkpoint-root .gmail-ingestion-control \
  --artifact-root .gmail-ingestion
```

Strict mode without automatic snapshot fallback:

```bash
gmail-ingest incremental --no-auto-full-resync
```

## Qualification boundary

This rc1 qualification is automated and uses synthetic Gmail clients and local persistence.

It does **not** assert that automatic recovery has already been exercised against a real Gmail
mailbox. A bounded real-mailbox scenario is retained as a stable `0.4.0` promotion gate.
